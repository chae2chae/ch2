02 Methods

방법별 핵심 · 장단점

세 방법 모두 pure odometry라 loop closure가 없고, 장거리에서 drift가 누적된다는 공통 한계가 있습니다.

FAST-LIO

v1 · 2021

핵심: iEKF의 Kalman gain을 측정 차원이 아닌 state 차원으로 풀어 high-rate LiDAR에서도 update를 빠르게 합니다.

장점

  • 가볍고 연산량이 적어 임베디드/소형 플랫폼에 유리
  • tightly-coupled 구조로 당시 기준 정확하고 빠름

단점

  • feature 추출 의존으로 식생·터널 등 feature 빈약 환경에 약함
  • 맵이 일반 kd-tree라 갱신 비용이 큼
  • 거의 모든 면에서 v2가 상위 호환

FAST-LIO2

2022 · default

핵심: feature 추출을 제거하고 raw point 직접 정합과 ikd-Tree(incremental insert/delete/rebalance)를 사용합니다.

장점

  • feature-free라 비정형/degraded 환경에 강건
  • ikd-Tree로 맵 갱신이 빠르고 실시간성이 좋음
  • 정확도·속도 균형이 좋고 생태계가 가장 두꺼움

단점

  • frame 기반 + IMU as input 구조라 IMU 포화·극격렬 모션에 취약
  • kHz급 출력은 어려움
  • pure odometry라 drift와 loop closure 부재는 그대로 남음

Point-LIO

2023 · aggressive motion

핵심: 각속도·가속도를 state에 포함(random-walk)하고, IMU를 input이 아니라 해당 state에 대한 measurement로 사용합니다.

장점

  • prediction이 IMU 적분과 분리되어 point-by-point, ~kHz 출력 가능
  • IMU saturation 강건성이 핵심 장점. 포화값을 reject/down-weight 가능
  • 고대역폭 제어 루프에 적합

단점

  • process noise Q가 새 민감 파라미터로 등장해 튜닝이 성능을 좌우
  • 일반적인 완만한 motion에서는 이득이 제한적
  • 포화 임계값과 노이즈 특성이 필요해 캘리브레이션 부담이 생김

04 Backend

SLAM / Navigation에 쓰려면

전제: 이 세 개는 front-end odometry입니다. loop closure도 global 최적화도 없습니다.

장거리에서 drift가 쌓이고 같은 장소를 다시 와도 자동 보정되지 않습니다. 용도에 맞는 back-end를 추가로 붙여야 합니다.

B · Navigation사전 맵에서 relocalization(map→odom)을 수행합니다. 예: FAST-LIO-LOCALIZATION. Mapping 모드와 Localization 모드를 분리합니다.

TF 트리

map→ odom→ base_link→ sensor frames
odom → base_link : LIO(FAST-LIO2/Point-LIO)가 high-rate로 publish
map → odom : localization / loop-closure back-end가 publish하는 drift 보정분

즉 LIO는 odom→base_link만 책임지고, 전역 일관성(map→odom)은 back-end가 채웁니다. 이 분리를 지켜야 nav stack이 깔끔하게 동작합니다.
